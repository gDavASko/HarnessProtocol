# План внедрения: Goal-контракт и повторяемые workflow-профили

## Цель

Добавить в Harness лёгкий, обратносуместимый слой для проверяемых целей и повторяемых схем оркестрации. Существующие state machine, validator, drift-guard, human gates и разделение `code`/`text` остаются источником исполнения и валидации.

## Границы

- Не добавлять автономный режим, который масштабирует каждую задачу без явного scale gate.
- Не менять правила human gate, внешнего независимого judge и запрет на self-validation.
- Не менять Unity-код и `.meta`-файлы.
- Не использовать worktree, ветки или controlled merge: все разрешённые изменения выполняются в текущем рабочем дереве только последовательными фазами.

## Этап 1. Goal-контракт узла roadmap

1. В `Scripts/harnessState.js` добавить нормализацию поля `goal` для каждого узла.
2. Поддержать поля:
   - `outcome` — одно измеримое конечное состояние;
   - `proof` — команда или иной способ доказательства;
   - `constraints` — неизменяемые границы;
   - `max_no_progress` — число последовательных итераций без улучшения;
   - `on_limit` — только `CRITICAL_FAIL`.
3. Сохранить прежнее поведение для уже созданных roadmap: при отсутствии `goal` использовать существующие `dod`, `max_iterations` и `validation_type`.
4. Отображать краткое состояние цели в синхронизируемом Markdown roadmap.
5. В `Scripts/roadmapEdit.js` добавить команды/опции для записи Goal-контракта без ручного редактирования JSON.

## Этап 2. Scale gate и workflow-профили

1. Добавить чистый модуль выбора масштаба, не запускающий агентов и не меняющий рабочее дерево.
2. Результат выбора: `classic`, `goal_loop` или `workflow`.
3. Решение основывать на количестве независимых частей, наличии детерминированного oracle, типе артефакта, критичности и явном переопределении пользователя.
4. Ввести декларативные JSON-профили в `HarnessProtocol/Workflows/profiles/`:
   - `unity-compile-fix`;
   - `readonly-code-audit`;
   - `safe-migration`;
   - `research-map-reduce`.
5. Каждый профиль фиксирует фазы, разрешённые типы действий, максимальное число работников, лимит общего бюджета и требуемую валидацию. На первом этапе профили являются машиночитаемыми шаблонами, а не обходят существующие permission/human gates.

## Этап 3. Runtime, лимиты и наблюдаемость

1. Выполнять разрешённые profile-фазы через runtime fan-out: до 3 read-only работников одновременно; write-фазы всегда последовательно в текущем рабочем дереве.
2. Ввести безопасные начальные значения: до 3 работников одновременно, до 8 работников на запуск, без повышения уже установленного бюджета узла.
3. Учитывать token budget по фазам и останавливать запуск до превышения лимита с машиночитаемой причиной.
4. Добавить в статус roadmap выбранный режим, профиль, фазовый расход и причины scale gate.

## Этап 4. Проверки

1. Дополнить детерминированные тесты для нормализации Goal-контракта, обратной совместимости и CLI-редактирования.
2. Добавить unit-тесты для scale gate и всех четырёх профилей.
3. Запустить smoke suite Harness и новые тесты Node.js.
4. Перед завершением привлечь независимый read-only judge для проверки изменения протокола и тестовых доказательств.

## Порядок поставки

Первая поставка реализует все этапы 1–4. Runtime запускается только для профилей с разрешёнными read-only фазами; изменяющие фазы не распараллеливаются и не используют worktree.

## Критерии готовности

- Старые `.harness_roadmap.json` загружаются без изменений.
- Новый Goal-контракт нормализуется и редактируется только через `roadmapEdit.js`.
- Scale gate выбирает воспроизводимый режим и не может превысить заданные лимиты.
- Все профили проходят схематическую валидацию.
- Детерминированные тесты Harness проходят успешно.
- Независимый judge не находит блокирующих проблем.
